## Question and frozen reference

Measure how the existing cap-24 acquisition/terminal-safety reference performs
on newly declared challenging V2 inputs, with raw and reflection adapters
reported separately. A lower rate than the gentle V1 learning set is a harder
input distribution, not evidence of a code regression or an RL advantage.
Use the same physical admitted inventory for both adapters. No controller,
planner, correction-cap, command timing or reflection-rule tuning is part of
this scope. Bind source/executable/configuration before generating final inputs.

The primary question is performance on the declared **layered broad** population.
Value noise is a separately measured backend contrast, not a second family quota
or an automatically averaged headline. Both backends have been exposed during
input calibration; do not call value noise unseen by the designer. Future RL
backend-transfer claims additionally require that its training/tuning exposure
exclude that backend. Fresh seeds alone establish no recipe shift.

## Prerequisites and ownership

1. Close the input-resolution decision before freezing. Keep the 4 m physical
   polyline explicitly authoritative if that is the intended envelope. Diagnose
   the seven raw-reference warnings by feature mechanism, using at most 128
   additional input inspections, with new sampling/QA declarations before any
   new inputs. Include independent representatives; no seven-case recipe repairs.
   If controls, sampling or thresholds change, create a new recipe/spec identity
   and preserve the current pilot. Sample agreement remains no continuous bound.
2. Declare the stress recipes/panels and their physical constraints before
   generation. Candidate targets are close obstacles beside wide pads, tight
   crest spacing, close obstacles beside narrow destinations and long sustained
   obstructions. Diagnose whether sparse combinations are structurally possible;
   use bounded continuous subranges/compositions, never authored flight corridors
   or controller-success admission. Record shortfalls without refilling budgets.
3. Extend the **composition** frontdoor in `pd-benchmark` to consume versioned
   manifests. The common evaluator already loads V2 physical scenarios and binds
   excluded proposal files; the incumbent CLI/report composition remains V1-only.
   Preserve `IncumbentAdapterV1::execute` and its configuration. Add truthful
   versioned report projections for morphology/geometry; do not disguise V2 as
   V1 `terrain_stratum` or drop mixed/unclassified inputs. Reuse maintained rich
   batch/detail/paired navigation. Mission generation and `pd-python` must not
   import the incumbent or its planner.
4. Freeze serialized requests, metric/admission versions, support interpretation,
   schedules, panel memberships/weights and source identity in Git before final
   generation. Maintain an exposure inventory across all prior training,
   development, validation and inspected proposals, including excluded inputs.
   Allocate previously unused seeds only at that checkpoint. Check exact physical
   duplicates across final populations and the exposure inventory; record any
   collisions and reduced counts without generating replacements.

These steps are completion gates for the next scope, not unfinished controller
work in the current mission-platform implementation. No reference controller's

Keep the existing eight-attempt structural limit per proposal. Structural attempts
are input-generation work, not additional flight opportunities. The observed
pilot yields suggest roughly 1,650 admitted broad inputs per 2,048-proposal
stream, but achieved counts govern all reporting. The stress union may be much
smaller than 512 and subgroup counts overlap. Do not run until a target landing
count is achieved, fill mild inputs into a challenge panel or silently add retries.

under both adapters is a paired comparison, not two independent samples. Raw

## Acceptance and interpretation

The 16-input frontdoor stage includes both physical directions, mixed and
unclassified cases, all three challenge paths and explicit unsupported/error
dispositions. Exercise identical fixed-command inputs through native/Python
paths, V1 byte/identity preservation, V2 excluded-file drift and canonical
reflection evidence. Stop before qualification if evidence boundaries fail;
record the failed stage rather than modifying frozen cases.

For every executed attempt retain physical input identity, native mission
assessment, unchanged-source/input integrity, command/stop/resource evidence
and independent replay. A reported landing requires the complete tuple.
Preflight rejection, preparation/capture failure, unsupported input and native
mission failure retain their exact scheduled slots. A zero-command stop is not
an executed landing; an interrupted run is not an ordinary completed miss.

Report each population separately: admitted-input and scheduled-attempt counts,
verified target landings, unsupported/error/unexecuted counts, then support-
conditional rates. Give each adapter's direction and geometry-conditioned views.
Keep broad versus stress versus backend contrast denominators explicit; overlapping
labels/panels cannot be summed. Keep all collection selection exclusions visible
in input-accounting views without counting excluded proposals as flight attempts.

For completed broad populations, sampling intervals concern the declared
proposal distribution conditional on admission. At about 1,650 independent
admitted inputs a worst-case 95% binomial interval is approximately ±2.4 percentage
points; use the achieved count and a declared interval method in the final report.
This is no bound on unmeasured terrains. Paired raw/reflected differences require
paired outcome accounting; mirrored runs and stress quotas are not independent
broad draws. With one fixed incumbent, no training-seed uncertainty is estimated.

Inspect held-out previews only after definitions and the unchanged reference
are frozen, preferably after the campaign. Any resulting tuning makes those
inputs development evidence for a future run. Preserve this run's original
outcomes and rich details. Publication is a separate operation after review;
server lifecycle and accepted navigation remain outside the campaign budget.

The result can justify a subsequent independent RL experiment by identifying
generic failure mechanisms and attainable coverage gaps. It cannot establish
complete terrain coverage, prove every admitted mission solvable, or validate an
RL approach that was never trained/evaluated in this scope.
